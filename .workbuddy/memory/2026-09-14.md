## 三、诊断：「为什么用不了 pnpm」

1. **根因**：`corepack enable` 从未执行过，PATH 上没有 `pnpm` 命令。PATH 里的 `%LOCALAPPDATA%\pnpm\bin`（= `PNPM_HOME`）只有全局包垫片（`create-next-app`、`opencode`）。两套 Node（workbuddy 托管、nvm `.nodejs`→`.shim`）都没有 pnpm 垫片。
2. pnpm 本体存在于 corepack 缓存 `%LOCALAPPDATA%\node\corepack\v1\pnpm\11.21.0\`。
3. **修法**：`corepack enable pnpm` → 生成 `pnpm` / `pnpm.CMD` / `pnpm.ps1` 到托管 Node 目录（PATH 第一个 node）。实测 `pnpm -v` / `pnpm.cmd -v` → `11.21.0`，`pnpm store path` → `E:\.pnpm-store\v11`，`pnpm ls` 正常。
4. **install 失败的真正报错**：`attempt to write a readonly database`（`ERR_SQLITE_ERROR` errcode 8，栈在 `StoreIndex.setRawMany` → `flush`）。根因是**被 kill 的上一次 install 进程未真正退出**，僵留占用 store 索引（PID 18540 命令行 `node pnpm.cjs install --prefer-offline`）。`Stop-Process` 后 `EBUSY` 句柄释放。
5. 旁证：`registry.npmmirror.com` 单请求 26–30 秒（`[WARN] Request took 29829ms`），首次 16 分钟未 link 完属正常。
6. **教训**：不要用「杀掉进程」终止慢的包管理器安装 —— Windows 上会留下持有 SQLite store 句柄的僵尸进程，把后续 install 全部污染成 readonly 错误。

### 环境坑：`node_modules/.bin` 的 .CMD 垫片在沙箱里无法执行

`pnpm typecheck` / `pnpm lint` / `pnpm test` 全部失败，报 **`拒绝访问。`（EACCES）**，而不是代码问题。已定位：

- `tsc` 垫片内容指向 `node_modules/@typescript/native/bin/tsc`（44 字节，`#!/usr/bin/env node` + `import "../lib/tsc.js"`）。
- **编译器本身完全正常**：`node node_modules/@typescript/native/bin/tsc --version` → `7.0.2`；`node node_modules/typescript/lib/tsc.js --version` → `6.0.3`。
- 但用路径调用 `.CMD` 就必然 EACCES：`& ".\node_modules\.bin\tsc.CMD" --version` → 拒绝访问。同一个模式下 `& "...\pnpm.CMD" -v` 也曾报同样错误，而裸 `pnpm.cmd -v` 正常。
- **绕法：跳过垫片，直接调 JS 入口**（本会话实测可用）：
  - `node node_modules/@typescript/native/bin/tsc --noEmit`（TS7 native，快）
  - `node node_modules/typescript/lib/tsc.js --noEmit`（TS6 classic）
  - `node node_modules/eslint/bin/eslint.js .`
  - `node node_modules/prettier/bin/prettier.cjs --check .`
  - `node node_modules/vitest/vitest.mjs run`
  - `node node_modules/prisma/build/index.js generate`（`pnpm prisma generate` 本身是能跑的）
- 判断：这是**沙箱对 .CMD 转发的限制**，不是项目缺陷，估计在用户自己的终端里 `pnpm typecheck` 正常。需用户在自己终端复核一次。

### 双 TS 编译器的事实（避免以后再困惑）

`package.json` 里两个 TS 是交叉别名的，`.bin` 里各有垫片：

- `typescript` = `npm:@typescript/typescript6@^6.0.2` → 经典 TS，bin 名 `tsc6`（`.bin/tsc6`）
- `@typescript/native` = `npm:typescript@^7.0.2` → 原生 TS，**占用了 `tsc` 这个 bin 名**（`.bin/tsc`）
- `@typescript/native` 的平台二进制由 optionalDependencies 提供，本机装的是 `@typescript/typescript-win32-x64@7.0.2`（在 `.pnpm` 内）。
- 实测两套都对本项目给出 0 类型错误，可放心使用；但要知道 `.bin/tsc` 是 TS7 而非 TS6。

**补充（14:14 复测）：TS7 native 在沙箱里会间歇性被拦**，报 `spawnSync ...\@typescript\typescript-win32-x64\lib\tsc.exe EPERM`。因为 `@typescript/native/lib/tsc.js` 只是 `execFileSync` 那个原生 exe，沙箱不允许 spawn 它。**类型检查请固定用纯 JS 的 TS6**：

```
node node_modules\.pnpm\@typescript+typescript6@6.0.2\node_modules\@typescript\typescript6\lib\tsc.js --noEmit
```

### 驳回（附理由）

- **缺陷 2「image 统一成 `string | null`」→ 会引入 bug。** 评审说 `profileSchema` 里的 `z.literal('')` "永远不会被触发"，这是把**表单层 schema** 和**传输层 schema** 混为一谈了。`profileSchema` 校验的是 RHF 的表单值 —— 用户清空输入框时值就是 `''`，`z.literal('')` 正是承载"清空头像"的那一支。改成 `z.union([z.url(), z.null()])` 后，清空输入框会报 "Enter a valid image URL"。**要达成评审的真实目标，正确做法是 `register('image', { setValueAs: v => v.trim() === '' ? null : v })`**，让 RHF 直接持有 `null`。我没做，因为它改动面大且运行时行为无法用现有测试覆盖。当前"表单 `''` → 提交转 `null`"只有一个转换点，本身不算缺陷。
- **缺陷 3「删掉 server schema 的 `z.literal('')`」→ 非缺陷。** 传输层确实收不到 `''`，但这是信任边界上的宽容，删掉只换来"少一个分支"。另外评审给 `username` 保留 `''` 的理由（"用户主动清空时需要发 `''`"）也是错的 —— 客户端是**省略该字段**（`...(username ? { username } : {})`），从不发空串。
- **缺陷 7「用 Proxy 惰性化 prisma adapter」→ 拒绝。** 评审自己也承认 CI 已设 placeholder 故当前不触发。为一个不发生的场景加一层 Proxy，恰好违反它引用的 Karpathy 原则。
- **缺陷 9「删掉 `link.tsx`」的前提是错的。** 评审称它"强制所有 import 它的地方进 client bundle"—— 但 `next/link` **本身就是 client component**，直接 import 也会进同样的 bundle，这层壳零成本。按评审自己给的"二选一"，选了加注释。
